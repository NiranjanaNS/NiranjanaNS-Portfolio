# User Personas

## Purpose

This document defines the main people who will use or evaluate NiranjanaNS Engineering Journey.
Each persona helps us make better decisions about content, navigation, performance, and depth.

## Persona 1: Recruiter

### Context

A recruiter is screening many candidates quickly and needs to decide whether this portfolio is
worth forwarding to a hiring manager.

### Needs

- Understand the candidate's role quickly.
- See strongest skills and projects.
- Access resume, GitHub, LinkedIn, and email without friction.
- Confirm that the portfolio loads fast and feels professional.

### Pain Points

- Too many portfolios look the same.
- Many portfolios hide key information behind unnecessary effects.
- Recruiters do not have time to decode complex navigation.

### What This Portfolio Must Do

- Communicate identity within 10 seconds.
- Make resume and contact actions obvious.
- Keep the project section scannable.
- Avoid confusing navigation.

## Persona 2: Engineering Manager

### Context

An engineering manager wants to understand whether Niranjana can think beyond UI screens and
contribute to real product development.

### Needs

- Project complexity.
- Architecture decisions.
- Code quality signals.
- Ownership and problem-solving ability.
- Evidence of maintainability.

### Pain Points

- Portfolios often show polished cards but little engineering depth.
- It is hard to evaluate real contribution from screenshots alone.
- Architecture and tradeoffs are often missing.

### What This Portfolio Must Do

- Include architecture and case studies.
- Explain tradeoffs and lessons learned.
- Link to GitHub repositories.
- Show testing, deployment, and performance thinking.

## Persona 3: Developer or Technical Interviewer

### Context

A developer or interviewer may inspect the project before or during an interview.

### Needs

- Clear source code links.
- Technical documentation.
- Interesting implementation details.
- Honest notes about mistakes and improvements.

### Pain Points

- Many portfolios overclaim skill depth.
- Project descriptions are often too vague.
- Code structure is not always easy to understand.

### What This Portfolio Must Do

- Use specific project explanations.
- Show folder structure and system diagrams.
- Keep engineering notes honest.
- Make the repository easy to navigate.

## Persona 4: Freelance Client

### Context

A freelance client is less technical but wants to know whether Niranjana can build trustworthy,
usable software.

### Needs

- Professional presentation.
- Clear examples of previous work.
- Simple contact path.
- Confidence that the developer communicates well.

### Pain Points

- Technical portfolios can feel intimidating.
- Clients may not understand architecture-heavy language.
- Contact information is sometimes hidden.

### What This Portfolio Must Do

- Keep language clear.
- Show outcomes and value, not only technologies.
- Make contact simple.
- Present work with trust and polish.

## Persona 5: Future Niranjana

### Context

Future Niranjana will update the portfolio with new projects, achievements, case studies, and
design improvements.

### Needs

- Easy maintenance.
- Clear folder structure.
- Reusable components.
- Documentation of decisions.
- A record of learning and growth.

### Pain Points

- Personal sites often become hard to update.
- One-off components make redesigns painful.
- Forgotten decisions create confusion months later.

### What This Portfolio Must Do

- Keep content data-driven where possible.
- Maintain a decision log.
- Use an engineering journal.
- Organize code by shared UI and feature sections.

## Decision Rules From Personas

- Recruiters need speed and clarity.
- Managers need engineering proof.
- Developers need technical honesty.
- Clients need trust and simplicity.
- Future Niranjana needs maintainability.

If a feature does not serve at least one of these users, it should be questioned before we build it.
